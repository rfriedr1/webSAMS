# CLAUDE.md

## Project Purpose
- Create a laboratory LIMS software as a Python web application.
- Legacy delphi code (from a previous legacy LIMS system used in the laboratory) can be used as inspiration but new workflows, logics and design patterns should be/need to be explored
- UI/UX should be improved for browser use.
- Preserve clear OOP structure and maintainable layering.

## Repository Context
- Legacy reference code (read-only reference): `../delphi-code`
- Database schema notes: `schema_summary.md`
- Domain glossary and bounded vocabulary: `CONTEXT.md` — read this first before naming new things; flagged ambiguities are listed at the bottom.
- Architecture decision records: `docs/adr/` — sequentially numbered. Don't re-litigate decisions here without checking these first.

## App purpose
- the app serves as the main Laboratory Management and Information System (LIMS) of our radiocarbon laboratory
- use modern design patters regarding LIMS and regarding UI/UX
- Navigation between pages and data records needs to be easy and logical

## Domain Model
- One `Submitter` can have many `Projects`. (DB table is `user_t` for legacy reasons; see `docs/adr/0001-submitter-naming.md`.)
- One `Project` can have many `Samples`.
- One `Sample` can have many `Preparations`.
- One `Preparation` can have many `Targets`.
- `Targets` hold the information of the graphitization procedure and also the analytical results (C14 age etc etc) optianed from that target

## App Architecture
- `sams_web/main.py`: FastAPI app setup
- `sams_web/models.py`: SQLAlchemy ORM models. Class names use domain language (`Submitter`); table names stay legacy (`user_t`).
- `sams_web/repositories.py`: DB access/query layer
- `sams_web/sample_import/`: Excel submission-sheet import (see "Sample Import" below)
- `sams_web/services.py`: business logic/workflows
- `sams_web/detail_update.py`: generic single-entity form-update primitive (`apply_detail_update` + `DetailUpdateConfig` per entity). All write paths flow through here; per-entity configs live next to the viewmodels.
- `sams_web/detail_page.py`: generic detail-page context builder (`build_detail_page_context` + `DetailPageConfig`). Read side of detail pages.
- `sams_web/preparation_bench.py` / `graphitization_bench.py`: bench workflow modules (`PreparationBench`, `GraphitizationBench`) — page_view() + save() + (graph) assign_graph_batch().
- `sams_web/ea_checks.py`: daily EA checks — settings (`EaCheckSettingsStore`), pure rules (`evaluate`, `summarize`, `passing_streak`), the `EaCheckLog` facade the routes use, and `EaCheckSignoffSubject` (see "EA Checks and QC Sign-off" below).
- `sams_web/access.py`: the access seam — `Permission`, `Role`, `current_user()`, `guarded()` for write routes, `can()` for templates (see "Access and Permissions").
- `sams_web/record_actions.py`: record actions — the `RECORD_ACTIONS` registry, `plan()` (preview, rolled back) and `apply()`; routes in `routers/pages_record_actions.py`, UI in `_record_actions.html` + `js/record-actions.js` (see "Record Actions" below).
- `sams_web/qc_signoff.py`: generic QC sign-off engine (`QcSignoffs`, `SignoffSubject` registry). `sams_web/lab_staff.py`: Setup → Lab Staff (operator chips, `may_sign_off`).
- `sams_web/sample_photos.py`: sample photos from the shared folder — settings store, background folder index, and the `SamplePhotos` facade the routes use (see "Sample Photos" below). No database access.
- `sams_web/setup_handlers.py`: one `SetupSectionHandler` per Setup section (see "Settings and Setup").
- `sams_web/magic_nav.py`: sealed `NavTarget` family + parser + match-based dispatchers for the magic-nav input.
- `sams_web/search.py`: `SearchContext` registry + `run_search()` + `fk_based_link()` rule for cell-level row links.
- `sams_web/routers/pages.py` and the per-area `pages_*.py`: server-rendered web routes (thin dispatchers).
- `sams_web/routers/api.py`: JSON API routes
- `sams_web/viewmodels/detail_sections*.py`: detail-page field grouping/formatting + per-entity configs (`SUBMITTER_DETAIL`, `PROJECT_DETAIL`, etc. for write; `*_DETAIL_PAGE` for read).
- `sams_web/templates/*`: Jinja templates. `_detail_fields.html` holds the detail-page macros: `render_detail_field_row` and **`render_detail_sections`** — the fact sheet every detail page renders through (never hand-write that loop again; it was copied five times before). `_detail_chrome.html` holds `render_record_head` (the shared record header), the saved-status pill, `render_pending_bar` (the record's Cancel / N unsaved changes / Save bar), notices and quick-nav. `lab_queue.html` owns the lab queue tables and *includes* `_preparation_bench.html` / `_graphitization_bench.html`, matching the `preparation_bench.py` / `graphitization_bench.py` split.
- `sams_web/static/app.js`: shared table-tools etc.
- `sams_web/static/js/*.js`: per-feature modules (toast, page-progress, detail-shortcuts, searchable-select, navigation-ui, magic-nav-ui, history-back, table-tools, detail-edit-mode, anchor-details, tab-panels, prep/graph bench UIs).
- `sams_web/static/style*.css`: split per concern. The global bundle (`_CSS_BUNDLE_FILES` in `main.py`, in this order) is `style-core` (tokens, base, header, trail, `.panel-bar`), `style-tables`, `style-detail-pages`, `style-components` (badges, status pills, shared responsive overrides), `style-setup`, `style-dashboard`. Page-only sheets load through `extra_styles`: `style-benches`, `style-ea-checks`, `style-photos`, `style-import`. A new sheet for every page goes into the bundle list; there is no `style.css` entrypoint any more (removed 2026-11, it was unused).

## Data Access Strategy
- Use a pragmatic hybrid approach.
- Prefer ORM for entity-centric CRUD/detail flows (users, projects, samples, preparations, targets).
- Use raw SQL (or SQLAlchemy Core) for complex queue/search/report/worklist queries where SQL is clearer and/or more performant.
- Keep all DB access inside the repository layer and avoid query logic in routers/templates. (Global search's SQL moved there too: `SamsRepository.search_table`; `search.py` only holds the context registry. The one deliberate exception is the import transaction in `sample_import/commit.py`.)

## Runtime and Configuration
- Python environment: `.venv` (local virtual environment)
- Install: `pip install -e .`
- Start app: `uvicorn sams_web.main:app --reload --port 8502 --log-config sams_web/log_config.json` (or `./start_webapp_macos.sh`). **The app runs on port 8502**, not uvicorn's default 8000 — both start scripts default to it; override with `PORT=…`.
- Default env examples in `.env.example`
- **Servers**: install from `requirements.lock.txt` (exact pins) + `pip install --no-deps -e .`, start with `start_server_windows.bat` (no `--reload`, no package installs, binds `0.0.0.0`, one worker, honours `.env`). The full procedure is `docs/server_installation.md` — **update it whenever the port, env vars, settings path, start command or dependencies change.** `start_webapp_*.{bat,sh}` are the **quick-start launchers** (`docs/quickstart.md`): they refuse to start without `.env`, install from `requirements.lock.txt` only when its hash changed (stamp in `.venv`), never override `SAMS_SETUP_DATA_FILE`, and run without `--reload` unless `SAMS_DEV=1`. **Default host differs on purpose:** the Windows launcher binds `0.0.0.0` (lab PCs can connect; `HOST=127.0.0.1` to restrict), the macOS one `127.0.0.1` (`HOST=0.0.0.0` to share). Keep the three docs (`quickstart.md`, `server_installation.md`, README) in step with the launchers.
- **Regenerating the lock** after a deliberate upgrade: `pip freeze --exclude-editable`, then re-add the two platform markers — `uvloop` has no Windows build (`; sys_platform != "win32"`) and `colorama` is Windows-only.
- **No login exists yet**: the app must stay on the lab network. Planned: IIS in front with Windows Authentication (guide §13).
- `SAMS_ACCESS_ROLE` (`admin` default · `editor` · `viewer`): the role every request gets until login exists — see "Access and Permissions".
- **Supported Python: 3.14 and 3.13 are tested** (full test suite + route sweep + Excel import on 3.14); 3.11/3.12 work. Every pin in `requirements.lock.txt` has a cp314 `win_amd64` wheel, so Windows installs need no compiler — re-check that on PyPI before adding a compiled dependency. The launchers prefer the newest tested version (`py -3.14`, then 3.13…, then `py -3`); a `.venv` keeps the Python that created it, so switching versions means deleting `.venv`.
- **Console branding**: every launcher passes `--log-config sams_web/log_config.json`, which prefixes every log line with `webSAMS` and turns colour codes off — the Windows console printed uvicorn's ANSI colours as literal `[32mINFO`. The launchers also print a banner and set the window title. On startup the app logs one line with version, database (name + host, never credentials) and settings-file path (`main._startup_summary`, via the FastAPI lifespan). Any new way of starting the app should pass the same `--log-config`.
- **Client-hangup tracebacks are filtered.** On Windows, asyncio's Proactor loop prints a `ConnectionResetError` (WinError 10054) traceback from `_call_connection_lost` whenever a browser drops a kept-alive connection. `main._quiet_loop_exception_handler` (installed in the lifespan) drops exactly that report and forwards everything else to the default handler — don't widen it to all `ConnectionResetError`s.
- **App version** lives only in `sams_web/__init__.py` (`__version__`). `pyproject.toml` reads it dynamically; the header shows it next to the title (`app_version` template global), the startup log line and `/docs` print it. Bump it there on each release — the app reads the attribute directly, so no reinstall is needed.
- `.gitattributes` forces CRLF for `*.bat` on checkout — cmd.exe mis-parses LF-only batch files.
- Key variables:
- `SAMS_DATABASE_URL` — **required, no default** (`config.py` refuses to start without it). Format `mysql+pymysql://<USER>:<PASSWORD>@<HOST>/<DATABASE>`; the real value lives only in the gitignored `.env`. Never write credentials into a tracked file.
- `SAMS_SETUP_DATA_FILE` (default: `sams_web/setup_data.json`) — the **live** settings file. It is gitignored because it holds the SMTP password; on a server point it at an absolute path outside the checkout (e.g. `C:\ProgramData\webSAMS\setup_data.json`) so `git pull` never touches it.
- `sams_web/setup_data.example.json` is the secret-free, tracked snapshot. `SetupStore` reads it whenever the live file does not exist yet, so a fresh install starts with the lab's settings; the first save writes the live file. To carry a settings change into git, copy it into the example and blank every password.

## Page Design Language (read before building or reshaping a page)
The 2026-11 redesign (dashboard, detail pages, import wizard, benches, tables, header, Samples landing, Search, Analysis, Setup) followed one set of rules, because the old UI felt overwhelming: too many cards, values shown twice, boxes around everything. A new page follows them too. The local mockups in `docs/design/ui-review/` (untracked, real customer data) show the target look; for a big new page, sketch it there first.
- **Fact sheet, not cards.** Every value appears once. No headline/KPI card rows, no box per field, no explanatory subtitle under a title. Structure comes from small uppercase group titles (`.fact-group-title`) and one thin rule between columns (`.fact-columns`, `.landing-starts`), never from nested boxes.
- **The page starts with its job.** The global header and the trail (breadcrumb, Pin, Recent) already say where you are, so a page has no header panel that only repeats them (the benches and Lab → Analysis have none). A title line, when needed, is one of the existing three patterns; don't invent a fourth:
	- `.panel-bar` for list and tool pages and the dashboard (title · muted count · controls right).
	- `render_record_head` for a record.
	- the fold-away `<details class="table-collapsible">` summary for a queue table.
- **One panel per job**: a tool row, a table, an editor. Related records go in their own panel under the fact sheet (`.record-related`).
- **Controls are compact and look alike.** A search or lookup field is `.search-field` (icon, borderless input, ~2.3rem tall); bench and lookup steppers use `stepper_buttons`; selects with more than 8 options become searchable automatically. Button labels are short verbs (*Save*, *Show*, *Load*), because the section title already names the thing.
- **One action bar per form, same shape everywhere**: ghost *Cancel* on the left, one primary on the right (`.bench-actions`, `.setup-actions`, `.import-foot`). Never two primaries. Detail pages use the same shape in their pending-changes bar (`render_pending_bar`), shown only while a field holds an unsaved change.
- **Tables**: mark the container `data-table-filter` and let `table-tools.js` build the toolbar; editors and small key/value tables get `data-table-plain`. Render list cells with `table_cell(key, row)` from `_table_macros.html`: it formats the value and links the column to its record through one rule (`search.fk_based_link`, the `row_link` global), so never hand-write a `sample_nr → /samples/…` if-chain again (four drifting copies were removed 2026-11). Load the whole list, or add a server-side search and say when the list is capped ("First 200 results").
- **Text and colour**: tokens only (type scale, spacing, semantic colours). Uppercase only for group titles; field labels in Title Case (from `field_labels.py`), other UI text in sentence case; numbers with tabular figures. A status is never colour alone: add a word (*Low*, *N late*) or an icon.
- **Empty, error and capped states say what to do next**: an empty table names the action that fills it, and an error says why it happened and what to do about it. Empty values are the muted `—`.
- **A new page is wired into navigation**:
	- `navigation.py`: main/sub nav and `NAVIGATION_COMMAND_ENTRIES` (command palette).
	- a branch in `buildBreadcrumbs` (`navigation-ui.js`) so the trail reads `Module › page › record`.
	- `data-page-label` when the page's first `h2` is not its name.
	- a `FIELD_LABELS` entry (`sams_web/field_labels.py`) for new columns.
	- a Magic Nav command and `/help` when users will jump there often.
	- the `:focus-visible` list in `style-core.css` for new clickable classes.
	- a `css_v` bump.
- **Responsive**: works at 1440, 1024, 860, 640 and 390 px with no horizontal page scroll (tables scroll inside `.table-wrap`). At ≤640px controls grow to touch size and secondary bits (the Recent list, the ⌘K hint) drop out.
- **Verify by looking**: screenshot the page at desktop and phone width before calling it done, with every non-GET request blocked so nothing is written to the database, and compare it with the neighbouring pages.

## UX/UI Invariants (Keep Consistent)
- Use modern design patters regarding visual alignment and sizing of UI objects and logical separation of control groups  
- Use modern, clean, consistent typography and fact-sheet layouts (see "Page Design Language" above; the old card-based detail layout was retired 2026-11).
- Each internal page should display breadcrumb navigation for orientation and quick backtracking.
- Keep history-based back navigation on detail pages. Back navigation should alway show where to link back to.
- Use icons instead of labelled buttons if the function of the icons are easily recognizable (don't do this in the primary and secondary navigation bar)
- Any table should provide:
	- Search/filter
	- Column sorting
	- Download icon export (Excel-compatible)
	- Internal scrolling within table container (avoid excessive page scrolling)
- **The table toolbar is generated, never hand-written.** `table-tools.js` builds one compact row for every `data-table-filter` container (and every bare table): filter field with a search icon, column select (options from the header row), clear ×, then "N of M" and the download icon on the right; field labels are screen-reader only. Templates only mark the container (`data-table-filter`, optional `data-table-search-placeholder` / `data-table-download-name` / `data-table-search-initial`). Hand-written copies (lab queues, submitter page, dashboard) were removed 2026-11; they had drifted into three different looks.
- **A fold-away table (`<details class="table-collapsible">`) reads like a panel heading**: title, muted row count, small chevron — no tinted bar. `/projects` keeps *All Projects* open by default, because its server-side search box lives under that heading.
- No server-side pagination in UI tables (load full dataset; pagination, if needed later, should be client-side UX)
- Prefer inline links in tables for navigation to details (instead of row-click navigation).
- Keep link-column style consistent (underlined, colored, bold).
- In detail cards/views, align field values (text/number/date) to the right for scanability; keep comment/multiline fields left-aligned.
- **Detail rows whose value is longer than 24 characters stack**: label on its own line, value full-width and left-aligned (`.detail-field-row.is-long-value`, set in `_detail_fields.html` from the value's length). A side-by-side label/value pair only reads well while the value is short; institution names, addresses and e-mails otherwise wrap into ribbons. The rule is length-driven, so it holds for every entity. **Free-text fields that are usually long always stack**, whatever the value: they are listed per entity (`SAMPLE_STACKED_FIELDS` = sample label + label #, `PREPARATION_/TARGET_STACKED_FIELDS` = prep / graph batch, `USER_STACKED_FIELDS` = organisation, institute, e-mail, website, address lines, `PROJECT_STACKED_FIELDS` = project name) and passed as `arrange_sections(stacked=…)`, which sets `row.stacked`. Chosen from the live data (average 16–27 characters each); add a field there when its typical value is longer than ~15 characters.
- In detail cards/views, do not use per-field hairlines; use subtle divider lines only at explicit group transitions.
- **The field box (`.detail-field-shell`) is an editing affordance, not decoration.** A closed field is drawn with a transparent border and no fill, so a section reads as a plain label/value list; the box appears on hover of an editable row (with a pencil), when the field is open, dirty, failing or warning. Keep the border 1px transparent rather than removing it, so opening a field never shifts layout. (Before this, ~40 outlined boxes per detail page — most holding only `—` — were the largest source of visual noise.)
- **Field labels are Title Case** (`var(--text-sm)`, weight 600, muted; the words come from `field_labels.py`). Uppercase tracked text is reserved for `.fact-group-title` / `.card-group-title` and section heads, so structure outranks fields.
- **Empty rows collapse per section.** The row macro adds `.is-empty-value` when `row.value is none`; `detail-empty-fields.js` hides those rows (`.is-empty-hidden`) behind a per-section "N empty fields hidden" toggle whose state persists for the session. Revealing them is how an empty field is filled in; a row that is open or holds a change is never hidden (CSS: `.is-empty-hidden:not(.is-open):not(.is-dirty)`). Uses a dedicated class, not `hidden`, so that override can win without `!important`.
- **Detail pages have no edit mode (2026-11, ADR-0006).** An editable value opens in place on click or Tab (`detail-edit-mode.js`): the same field box switches from display to editor. A changed field stays open with its dirty dot; an unchanged one closes when focus leaves; Esc reverts the open field. Changes pile up and are saved together from the pending bar, which **posts only the changed fields** (unchanged controls are disabled just before submit; `apply_detail_update` leaves absent fields untouched). After a rejected save (422) the editors show the submitted values with `data-initial-value` = the stored value, so they come back still dirty. Last save wins — there is no conflict check. Leaving the record with changes (links, quick-nav, `[` `]`) asks Discard / Save / Keep editing; `window.SAMSDetailEdit` is the hook for other scripts.
- Change tracking looks only at **named** controls (the posted ones): the searchable-select combobox has no name, so filter text typed into it is not a change until an option is picked.
- Minimize layout shift when a field opens (stable row height); multiline/comment fields may expand when needed.
- Visually mark changed (dirty-dot) fields.
- Use the same dirty-dot visual pattern for task-focused bench UIs (e.g. `Preparation Bench Entry`, `Graphitization Bench Entry`) so users can quickly see unsaved changes and where they were made.
- Detail-page edit controls (`Edit`, `Save`, `Cancel`) should be right-aligned and visually lightweight (no persistent instructional hint text).
- When saving detail-page edits, show clear progress feedback on the `Save` button (spinner/loading state), and disable the pending bar's buttons to prevent double-submit while the request is in progress.
- Tables use `table-layout: auto` with `min-width: 100%`, so each column takes the width its content needs; `.table-wrap` scrolls horizontally when the total exceeds the panel. Never go back to `table-layout: fixed` — it split the width evenly and shredded long values (a project name got the same 109px as a 3-digit count).
- `td` uses `overflow-wrap: break-word`, never `word-break: break-word` / `overflow-wrap: anywhere`. The latter zeroes the cell's min-content contribution, letting an auto-layout column collapse below its longest word.
- `thead th` never wraps, so a column is always at least as wide as its own label.
- Date columns are detected from cell content by `table-tools.js` and tagged `.table-col-atomic` (nowrap + tabular numerals) — a hyphen is a legal break opportunity, so `2026-01-28` otherwise wraps to `2026-` / `01-28`.
- **Empty values render as a muted italic em-dash (`—`)**, never `Not set` or `null` or `N/A`. The dash uses `.detail-empty` styling (italic, low contrast). The detection helper is `viewmodels.detail_sections_common.is_empty_display_value(value)` — it returns True for `None`, blank/whitespace strings, sentinel string tokens (`"undefined"`, `"null"`, `"n/a"`, `"none"`), and **sentinel dates with year < 1950** (legacy null stand-ins like `1899-12-30`). All `format_*_value` formatters route through this helper. New value formatters should call it; new templates should render the `—` via `<span class="detail-empty">—</span>`.
- **Secondary detail sections sit in one "More details" block.** Sections with `placement == "more"` (sample: Record, Dates, Lab Workflow, Calibration, Storage) render inside one `<details class="record-more" open>` whose summary lists their titles. It is **open by default** since the fact-sheet redesign made the page light enough; the operator can still fold it.
- **No detail value may run past its column.** Each fact-sheet section's `<dl>` has `grid-template-columns: fit-content(45%) minmax(0, 1fr)` and its side-by-side rows inherit it through `subgrid`, so the label column is as wide as the section's longest label and every value / edit box starts at the same x (per-row sizing made the edit boxes ragged). Use `fit-content`, never `minmax(min-content, 45%)`, which the grid grows to its 45 % maximum whenever there is room (every label column was 45 % wide and a 16-character graph batch ran into the next column). Every box from the row down to `.detail-field-display` has `min-width: 0` and the display uses `overflow-wrap: anywhere`, so an unbreakable value (batch names, labels, e-mails) wraps inside its own column.
- **Sections whose every row is empty are dropped at build time.** Pass `drop_all_empty_sections=True` to `build_sections(...)` for verbose detail pages (sample currently uses this — preparation/target/project don't, by choice).
- **One label per field, on every page: `sams_web/field_labels.py` (`FIELD_LABELS`, `field_label(key)`).** Table heads (`format_table_header_label` is the same function), detail-page rows (`build_sections`), bench fields and the import wizard all read it, so a column is called the same everywhere. Before 2026-11 the table heads and each detail page kept their own dictionaries and 25 fields had drifted ("User Label" in the project's sample table vs "Sample Label" on the sample page, "d13C" vs "δ¹³C", "Cal 1s" vs "Cal 1σ"). Rules: labels are **Title Case** (the lab's choice, 2026-11 — sentence case was tried and rejected), short joining words stay lower case (*Free of Charge*, *Return to Sender*), acronyms and symbols keep theirs (FM, C14, δ¹³C, MA #); no per-entity overrides; **a template never spells out a field's label** — write `{{ field_label('key') }}` in a `<th>` or `<label>`. `tests/test_field_labels.py` fails on a hand-written label that names a field, on a model column with no label, and on a viewmodel that defines its own `*_FIELD_LABELS`. A label for something that is not a registry field but happens to share a name opts out with `data-own-label` (the EA check's standard *Weight*). Unknown keys (ad-hoc query aliases) fall back to `snake_case → Title Case`.
- **Related-records tables are keyed like list tables.** The project's sample table and the submitter's project table take their columns from `PROJECT_SAMPLE_COLUMNS` / `SUBMITTER_PROJECT_COLUMNS` (`detail_sections_user_project.py`) and their rows from `table_rows(...)`, and render through `field_label` + `table_cell`. Add a column by adding its key there.
- **Empty-state table rows** (`<td class="table-empty-row">`) use centred italic muted text and call out the relevant CTA (e.g. "Use **+ Prep** above to create one"). Don't ship the bare "No rows found" sentence.
- **Save / notice feedback fires as a toast** (top-right, auto-dismissing) via `window.SAMSToast.show(message, kind)` where `kind` ∈ `success | error | info`. The toast module also auto-promotes `?saved`, `?bench_saved`, `?graph_saved`, `?graph_batch_saved`, and any `*_notice` query params on page load and strips them from the URL via `history.replaceState`. Inline panel-head feedback is allowed alongside, but the toast is the primary surface.
- **Decorative animations and the blurred bg-shapes respect `@media (prefers-reduced-motion: reduce)`** — they're hidden / shortened for users who opted out.
- **Every interactive element has a visible `:focus-visible` outline** (`2px solid var(--brand-2)` with `2px` offset). When you add a new clickable thing, include it in the focus-ring rule list in `style-core.css`.
- **Three responsive breakpoints**: 1024px (large), 860px (medium), 640px (small). At 640px: cards stack to one column, inputs/buttons grow to ~44px touch targets, the header stacks (brand, then Magic Nav + Jump across the full width, then the nav). The header alone also has a squeeze step at 1025–1180px (product name and the ⌘K hint hide) so its single row still fits.
- **Header** (`base.html`, redesigned 2026-11 per the mockup in `docs/design/ui-review/`): **one row** — brand (SAMS mark, name, version, and a `.brand-db` tag with the database name from the `app_database` global, so test vs live is always visible), the flat main nav (`.main-nav a`, active = brand colour on `--brand-tint`), then on the right **Magic Nav and the ⌘K "Jump" trigger as two separate inputs**. The module's sub-nav is a thin second row of **underlined tabs** (`.sub-nav-row`). Both rows share the page width (`min(1240px, 96%)`). At ≤1024px the main nav moves to its own row. Merging Magic Nav and the palette into one field is a possible later step, not done.
- **The trail** (`.context-strip`) is one plain line under the header: breadcrumb text on the left; *☆ Pin*, Pinned and Recent as plain links on the right. Recent never lists the current page or a pinned one and shows at most 4 (3 at ≤1180px, 2 at ≤1024px, none at ≤640px); the command palette still has all 8.

## Magic Nav Rules
- Input only digits: treat as `sample_nr` and open sample detail.
- **One rule for prefixes: prefix, optional separator (`:`, space, or nothing), value.** Digits are a number; a value starting with a letter is a name (only for prefixes in `MAGIC_IDENTIFIER_NAME_PREFIXES`). The UI documents the **colon form** (`pr:456`, `sub:210`, `sub:meier`) and says the colon is optional; `pr456` / `sub210` keep working.
- Prefix `pr` + digits: treat as `project_nr` and open project detail.
- Prefix `sub` + digits: treat as `user_nr` and open submitter detail.
- Prefix `sub` + name (`sub:meier`): last-name lookup via `/submitters/lookup?name=` (`SubmitterNameNav`). **It never guesses**: exactly one record opens it; several (names repeat, and 267 people are stored more than once with different addresses) redirect to `/submitters?q=<name>`, which pre-fills the table search on the Last Name column (`data-table-search-initial` / `data-table-search-column`) and shows town + e-mail to tell them apart; none gives the inline error. Matching (`SamsRepository.find_submitter_nrs_by_last_name`): exact last name first, substring only when there is no exact hit. `user_t.last_name` is `latin1_swedish_ci` (ä ≠ a), so the query converts to `utf8mb4_unicode_ci` to fold case and accents; the table filter folds accents too (`SAMSUtil.foldForSearch`). `subotic` therefore means `sub` + `otic`: write `sub:subotic`.
- Magic commands:
- `/prep` opens `Lab/Preparation`
- `/graph` opens `Lab/Graphitization`
- `/ana` opens `Lab/Analysis`
- `/sub` opens `Samples/Submitters` (the list — distinct from the `sub<number>` prefix, which opens one submitter)
- `/proj` opens `Samples/Projects`
- `/import` opens `Samples/Import`
- `/ea` opens `Lab/EA Checks`
- Commands are matched *before* the `pr` / `sub` prefixes and always start with `/`, so a new command can never shadow an identifier form. Add one by extending `MAGIC_IDENTIFIER_COMMAND_ROUTES` + `..._LABELS` in `magic_nav.py`; the `/help` rules table is generated from those dicts, but the cheat-sheet overlay (`magic-nav-ui.js`), the command palette's own `magicCommandMap` (`navigation-ui.js`), the input's rotating placeholders (`base.html`), the `/help` prose list and `not_found.html` are hand-written and must be updated too.
- Unknown pattern: show `unknown ID`.
- Not-found IDs: show inline error in the patch area and do not navigate.
- Keep `/help` updated whenever Magic Nav behavior changes (prefixes, labels, validation, or routing targets).

## Detail Page field hierarchy
- **Detail pages are fact sheets, not card stacks** (redesigned 2026-11 because the cards made the UI feel overwhelming; mockups in `docs/design/ui-review/`, kept local and untracked because they show real customer data). Every value appears **once**. There are no headline cards and no headline builders any more: everything comes from the entity's sections (`build_*_sections` → `{name}_sections`).
- **Record header** (`render_record_head` in `_detail_chrome.html`): title + lighter subtitle (`Sample 48211  EIL R-EVA 3521`), a context line passed as the call body (back link, parent records, status pill — parent-record links for project / submitter / sample carry `.record-context-item.is-key` and render a step larger, because they are the main way out of a record), and on the right the page actions (`+ Prep`, `+ Target` as compact `.record-action` buttons, only when `{name}_can_edit`), quick-nav and the saved-status pill.
- **Fact sheet** (`render_detail_sections`): sections with `layout == "column"` sit side by side as columns (`--fact-cols`: up to 4, 2 at ≤1024px, 1 at ≤640px), separated by one vertical rule, titled by a small uppercase `.fact-group-title`. Sections with `layout == "wide"` (Comments, Notes) are full-width bands below the columns. No boxes: the field shell only appears on hover / when the field is open, where it *is* the input box (the control inside has no border of its own).
- **Layout hints come from the viewmodel**, not the template: `arrange_sections(sections, order=…, wide=…, more=…)` in `detail_sections_common.py` sets `layout` / `placement` and the order. `attach_readout(...)` lifts a read-only value ± sigma pair into `section["readout"]`, rendered as one figure (`5923 ± 25 BP`, `.fact-readout`) — used for the C14 age on sample and target. Never route an editable field through it: its rows are removed.
- Section titles stay short and noun-form. When adding a field, put it in the section whose title best describes it rather than adding a section; the most important section goes first in the spec / `order`.
- Related records live in their own panel below the fact sheet (`.record-related`, title + count chip): the sample page shows preparations with their targets as one tree table (`.record-tree`, `data-table-plain`, prep rows with target rows under them), the preparation page its targets, the project its samples, the submitter its projects.
- Current groups:
	- **Submitter** — Identity · Organisation · Contact · Address | Notes (wide)
	- **Project** — Core · Timeline · Submitter · Commercial · Logistics · Reporting | Comments (wide)
	- **Sample** — Identity · Classification · Other Analysis · Results (C14 age readout) | Comments (wide) | Photos strip | More details: Record · Dates · Lab Workflow · Calibration · Storage
	- **Preparation** — Batch & Timeline · Weights and Methods (incl. Yield) · Step Timeline · EA Data | Comments (wide)
	- **Target** — Graphitization · Elemental Analysis (incl. C/N Ratio and Total C (µg), warning when below the Lab Warning Threshold) · Results (C14 age readout, FM, d13C, magazine/position) · Calibration | Comments (wide)
- Empty values render as the muted italic `—` per the standard empty-value rule. Boolean fields render as the disabled-checkbox badge (`.detail-boolean-check`).

## Data Formatting Rules
- `C14 Age` and `C14 Age Sigma`: round/display as integers.
- `FM` and `FM Sigma`: round/display to 4 decimals.
- `d13C` and `d13C Sigma`: round/display to 4 decimals.
- `C (%)` (`conc_c`) and `N (%)` (`conc_n`): round/display to 1 decimal.
- `C/N Ratio`: calculate from EA values as `(conc_c/12.011)/(conc_n/14.007)` and round/display to 1 decimal.
- Boolean fields in detail cards: render as checkboxes (view mode).
- `stop` label in preparation/target detail views: `Discarded`.
- Empty / sentinel values: render as muted italic `—` (see UX/UI Invariants for the full empty-value rule).

## Frontend Modules and Shared Behaviours
- **Detail values come from the section rows, never raw ORM attributes.** Every displayed value routes through `format_*_value` via `build_sections`. Passing `sample.type` straight into a template leaks legacy sentinel strings like `"undefined"` and sentinel dates into the UI (the context line of the record header is the one place that reads parent records directly — keep it to names and numbers).
- **Global asset bundles**: `base.html` loads `/static/bundle.css` + `/static/bundle.js` (concatenated + minified in `main.py`, cached per process, `Cache-Control: immutable`). **Bump the `css_v` global in `routers/pages_shared.py` whenever any static asset changes** — it's the cache-bust signal. Bench CSS/JS load only on the bench page via `extra_styles`/`extra_scripts` blocks.
- **Page-specific JS registers into `window.SAMSAppInstallers`; `app.js` dispatches the list.** `app.js` ships inside `bundle.js`, which is the *first* deferred script, so its dispatch must wait for `DOMContentLoaded` — `document.readyState === "interactive"` is already true while later deferred scripts (the bench modules) are still pending. Running on `interactive` silently no-opped `installers.installGraphitizationBench?.()` and killed both bench UIs. Only `readyState === "complete"` may run immediately.
- **Never put data into `innerHTML` unescaped.** Build cells with `textContent`, or pass every interpolated value through an escape helper (`esc()` in `sample-import.js`). Sample labels come from customers' Excel sheets: the graphitization bench's staged-batch table interpolated `user_label` raw, and a label like `<img src=x onerror=…>` ran script for whoever staged that target (verified, fixed 2026-10).
- **`js/util.js` (`window.SAMSUtil`) is the first file in the JS bundle** and holds small helpers shared by bundled modules (`normalizeWhitespace`). Use it instead of re-declaring a helper in a second module.
- **`[hidden]` always wins**: `style-core.css` has a global `[hidden] { display: none !important; }` reset. Never work around it with a class-based show/hide; toggle the `hidden` property.
- **Design tokens**: type scale (`--text-xs` 0.72 · `--text-sm` 0.84 · `--text-base` 0.92 · `--text-md` 1 · `--text-lg` 1.18 · `--text-xl` 1.4 · `--text-2xl` 1.66 · `--text-3xl` 1.96 rem, plus `--text-h2/h3/h4`) and 4px spacing scale (`--space-1` … `--space-6`) live in `:root` in `style-core.css`. **Colours are semantic tokens too** — `--surface-tint`, `--brand-tint`, `--line-soft/-strong`, `--ink-strong/-soft`, `--brand-deep/-accent`, and the `--success-*` / `--danger-*` / `--warn-*` families, declared in `:root`. 380+ literals were folded onto them; near-identical shades (a few RGB units apart) were merged deliberately. A new hex literal is only acceptable when no token is within a hair of it. The ~100 that remain are each used once and are genuinely distinct (chart/status hues, one-off text tints); a second pass folded the 22 within 25 RGB units of a token. **Every text `font-size` must be a token** — the stylesheets were consolidated from 43 distinct literal sizes onto this scale, and a literal rem value is only acceptable for a glyph (stepper arrows, dirty dot, close ×, dropzone icon). Bands when choosing: xs = micro labels/badges, sm = labels, notes, table cells, base = field values and body copy, md = headings inside cards / buttons.
- **A capped list must never rely on the in-table filter for search.** `table-tools.js` filters only the rows already in the DOM, so on a truncated list it silently reports "no matches" for records that exist — searching *Friedrich* on `/submitters` found nothing because the first 500 rows alphabetically stopped at *Ebinger-Rist*. Either load the whole table or give the page a server-side search box; never a cap plus a client-side filter alone.
- `/submitters` **loads all rows** (~2 700 → ~846 KB / ~70 ms), so its one search box filters everything.
- `/projects` keeps the 500-row cap (12 985 rows render to ~9.2 MB, an order of magnitude worse) and instead has a **server-side** search form (`?q=`) covering project name, number, status and submitter, plus `?show_all=true`. `repositories.count_projects()` / `count_submitters()` back the honest "N of M" banners.
- **`TemplateResponse` always takes the request first**: `templates.TemplateResponse(request, "x.html", ctx)`. The old `(name, ctx)` form was removed in Starlette 1.0; all 28 call sites were migrated, the `<1.0` pin lifted (`<2.0` now), and the suite passes on Starlette 1.10 / FastAPI 0.162. `requirements.lock.txt` still pins the deployed versions — upgrading them is a separate, deliberate step.
- **Sub-nav rows only render for modules with 2+ destinations** — single-chip sub-navs that duplicate the main nav item are deliberately removed (`navigation.py`).
- **Toasts**: `window.SAMSToast.show(message, kind, { duration })`. `kind` defaults to `info`; `duration` defaults to ~4.5s, pass `0` for sticky. Auto-fires on save query params.
- **Keyboard shortcuts within a record** (active when the page contains `[data-edit-scope]`; `[` `]` / `j` `k` follow the quick-nav arrows by their `data-quick-nav="prev|next"` hook, never by class: the class-based lookup silently broke when the record header was redesigned): `Ctrl/Cmd + S` save the pending changes (always intercepted, even while typing; nothing happens without changes), `[` or `j` previous record, `]` or `k` next record (both ask first when there are unsaved changes), `?` open the cheat-sheet overlay. `Esc` inside an open field reverts it (handled in `detail-edit-mode.js`). Suppressed while typing in inputs (except Save) and while the unsaved-changes dialog is open.
- **Shared bench behaviour lives in `bench-common.js`** (`window.SAMSBench`): `installDirtyMarkers(form)` and `installLookupForm({bench, form, sampleInput, sampleStepAttr, currentSample, dependents})`, where `dependents` is the ordered list of fields that belong to the sample (`[Prep #]` on the preparation bench, `[Prep #, Target #]` on graphitization). Both bench scripts used to carry their own copy (66 identical lines), so a fix had to be made twice. Loaded before both bench scripts in `lab_queue.html`; put anything else both benches need there, not in either bench file.
- **Bench layout** (redesigned 2026-11 to the fact-sheet density; mockup in `docs/design/ui-review/`): both benches are built from the macros in `_bench_macros.html` — a lookup row (Sample # / Prep # / Target # with "of N", Load, and *Open full …* on the right), **one line of sample facts** (`ctx_item`, values through `format_table_cell_value`, extra facts as `.bench-chip`s), the entry fields as lab-flow stages (below), **flags as chips** (`bench_flag`; derived or project-owned flags are `bench_flag_readonly`, dashed and never posted), **extra analyses on both benches**: C/N isotope analysis (`CNIsotopA`) and dendro analysis (`DendroA`) sit in the sample facts line as read-only chips (`ctx_flag`, `.bench-analysis-chip`), **always shown**: Yes = solid amber chip with a check mark, No = quiet dashed chip with a minus — the lab needs "no" to be an answer, never a missing value, and "yes" impossible to overlook. Tried and dropped: a disabled checkbox (greyed out, tick unreadable) and a plain Yes/No word (too easy to overlook). Set in the import wizard or on the sample page, never on a bench, and shown once (not again in the Flags row), and one action bar: ghost *Cancel* left, *Save* + primary *Save & next* right. No headline cards, no page-header panel. ## Access and Permissions
- **`sams_web/access.py` is the one place that knows who the user is and what they may change** (ADR-0006). `Permission` = `edit_records` (detail pages, benches, import, EA checks, API writes) · `manage_setup` (Setup, test e-mail, maintenance) · `sign_off_qc`. `Role` = `viewer` (nothing) · `editor` (records + sign-off) · `admin` (all). "User" here is the person using the app; a customer is a *Submitter* (ADR-0001).
- **Until login exists** `current_user(request)` returns an anonymous `AppUser` with the role from `SAMS_ACCESS_ROLE` (default `admin`, i.e. everyone may do everything). With IIS + Windows Authentication only `current_user()` changes. The startup log line names the role.
- **Every non-GET route carries `dependencies=guarded(Permission.X)`.** `tests/test_access.py` walks `app.routes` and fails on a write route without a guard, and checks a viewer gets 403 everywhere. A 403 renders `forbidden.html` for browsers, JSON for `/api/`.
- **Templates hide write controls** with `{% if can("edit_records") %}` (template global, `pages_shared.py`); detail pages get `{name}_can_edit` from `build_detail_page_context`, and `render_detail_sections(..., can_edit=…)` renders editors only then. Where an action bar is hidden, a `.view-only-note` line says why; Setup shows its editor inside `<fieldset disabled>`. Hiding is courtesy — the guard is the check.
- **Change log comes with login**: every detail save passes `SamsService._apply_and_commit` with only the changed fields; that is where who/when/old → new will be recorded.

## Record Actions
- **A record action sets one field to one value on many records under a record page** (ADR-0007): *Set / Clear* C/N Isotope Analysis, Dendro Analysis, No Leftover on samples, No Leftover on preparations (project and submitter pages), Return to Sender / Prep Return to Sender on projects (submitter page); *Edit / Clear* Sample Storage Location and Prep Storage Location on samples (project page only). Glossary term "record action" — never "batch".
- **Edit actions** (`EditTextAction`, one `_TEXT_FIELDS` entry): the operator types the value per record. The preview answers `mode: "edit"` with an `editor` block — **every** record in scope (no 200 cap) with its current value, plus `refused` for records whose page would refuse any save (found by a dry run writing each record's own value back) — and the dialog shows one box per record, prefilled, with a *Fill all* field (prefilled when all records share one value), dirty dots and Enter moving down the list. Only changed rows are posted, as JSON in the hidden `values` field (`parse_values`); a ref outside the scope or a value over the column's length raises `ValueError`; an emptied box clears the value.
- **Owner, rows, child.** The owner is the page (`project`, `submitter`); its related table holds the rows the operator ticks (`OWNER_ROW_KIND`: samples, projects); the child is what gets written — the row itself or reached through it (`_reach`: preps of the ticked samples, samples of the ticked projects). No ticks = all rows; a ticked number outside the owner raises `ValueError` (never silently skipped).
- **Always preview, then run.** `plan()` runs the real checks and rolls back; `apply()` re-reads the database and commits. Both go through `SamsService.apply_many_and_commit` → `apply_detail_update` with the child's `DetailUpdateConfig`, so a record its own page would refuse (≈2 500 old samples lack type/material/fraction; the sample config also requires the project's In/Desired Date) is **listed with the reason and left alone**, and the rest commit together. Don't bypass the configs to "fix" that.
- "Clear" treats NULL as already clear. No run log / undo: the opposite action is the undo; the change log will hook into `apply_many_and_commit` with login.
- **UI:** `record_actions_menu(...)` (from `_record_actions.html`) goes into `render_record_head(actions=…)` only when `{name}_can_edit`; the related table gets `record_action_tick_head` / `record_action_tick`. The tick head carries `data-table-skip`, which `table-tools.js` honours (no filter option, not exported) — use it for any future control column. The preview dialog is built with `textContent` only. Menu entries are also `[data-command-link]` anchors to `#action=<key>`, so the command palette lists them with no palette change. Results come back as `?action_notice=` / `?action_error=` toasts. An action refuses to open while the fact sheet has unsaved changes (toast).
- **To add an action:** one `_FLAGS` entry (child, field, owners, optional warn), or one `_TEXT_FIELDS` entry for a free-text field. Its field needs a `FIELD_LABELS` entry and must not be read-only in its config — `tests/test_record_actions.py` checks both. A new owner page needs an `OWNER_ROW_KIND` entry, an `owner_rows` branch, two routes and the template wiring. Anything that is not "set field to value" subclasses `RecordAction`.

## Settings and Setup
- Store setup data in a generic settings file, not feature-specific filenames.
- Current settings file: `sams_web/setup_data.json`.
- Setup page should remain extensible for future configuration modules.
- **One handler per Setup section** (`sams_web/setup_handlers.py`). ## Lab Warning Thresholds
- The canonical list of in-app warning thresholds lives in `LAB_WARNING_THRESHOLD_FIELDS` in `sams_web/lab_warning_thresholds.py` — that tuple drives the Setup → "Lab Warning Thresholds" editor, the JSON persistence in `setup_data.json`, and the per-field formatting rules. Don't duplicate the list elsewhere; treat the code as source of truth and the Setup page as the user-facing rendering.
- Each threshold has its own evaluator in `sams_web/viewmodels/lab_warnings.py` returning a `WarningOutcome` dict keyed by the threshold's key. Evaluators are pure (no DB / no service / no request), so warnings stay easy to test and easy to extend.
- Detail-page integration is declarative: the entity's `DetailPageConfig` carries a `warnings_builder` callable, and `build_detail_page_context` exposes results as `{name}_warnings`. `build_detail_page_context` also indexes them by field as `{name}_warnings_by_field`, which the template passes to `render_detail_sections(..., field_warnings=…)`; the row macro tints the row (`.has-warning`) and shows the inline hint.
- To add a new warning: (1) append a `LabWarningThresholdField` entry, (2) extend the relevant `evaluate_*_warnings` function (or write a new one + wire it via `warnings_builder`), and (3) set the outcome's `field_key` to the row key of the field it concerns, so it lands on that row (and pass `field_warnings=` in the template if the entity doesn't yet). The Setup UI picks up the field automatically.

## Sample Import (Excel submission sheets)
- Customers return filled-in copies of `templates/Submit_Samples_Template.xlsx`. The importer reads the `.xlsx` **directly** — no CSV export step (that was a legacy Delphi limitation).
- Wizard at `/samples/import` (Samples → Import), five steps: **Upload → Review → Lab values → Extra analyses → Imported (+ e-mail)**.
- **Wizard layout** (redesigned 2026-11 to the fact-sheet density; mockup in `docs/design/ui-review/`): one header panel (title, file name + sheet facts + *Use a different file*, step indicator), one panel per block, and **one sticky action bar** (`.import-foot`) for steps 2–4 with a "Ready · …" / "Fix the items above" status and Back / Continue. Each part of the bar names its step (`data-foot-for="<stage>"`) and `setStep()` shows only the current step's parts. All wizard tables are editors and carry `data-table-plain`; sheet cells size to their longest value through the input's `size` (an input has no content width).
- Module layout in `sams_web/sample_import/`:
	- `vocabulary.py` — normalisation + fuzzy label matching, and the *built-in* heading synonyms.
	- `fields.py` — **the importable-field registry.** Built-in fields plus operator-defined ones resolved into one `FieldRegistry` (synonyms / labels / allow-list / lookup-backed set). `SAMPLE_TARGET_COLUMNS` is derived from the `Sample` ORM model, so a new model column is automatically available as an import target; `BLOCKED_TARGET_COLUMNS` keeps identity and BATS-owned result columns off-limits.
	- `workbook.py` — `.xlsx` → normalized `Grid` of `Cell`s; picks the submission worksheet by content score.
	- `parser.py` — finds the sample-table header by *scoring every row* against the registry's headings, then reads the metadata block above it as `label | value` pairs. **Nothing is addressed by fixed row/column index.**
	- `draft.py` — typed, JSON-serialisable results; every value carries its source cell address.
	- `matching.py` — submitter scoring (e-mail ≫ surname+organisation ≫ surname) and lookup resolution.
	- `commit.py` — the single transaction, as named steps: `_validate_payload` (rejects before any write) → `_resolve_submitter` → `_resolve_invoice` → `_resolve_project` (new, or append to existing) → `_create_samples` (uses `_build_sample_payload` per row) → one `session.commit()`. Each step returns a small frozen dataclass (`_Party`, `_ProjectRef`, `_ImportPlan`); `commit_import` itself is just the sequence. `mailer.py` — render + SMTP send. `service.py` — glue for the router.
- **Adding an import column needs no code change.** Setup → *Import Column Headings* has two parts: extra spellings for built-in fields, and *Additional columns* where the operator picks a target `sample_t` column, a label, and the headings that map to it. Stored in `setup_data.json` as `{"headings": {...}, "custom": [...]}`; the old flat shape is still read.
- **Layout flexibility.** Header row = whichever row scores ≥ 2 recognised columns (`MIN_HEADER_MATCHES`). Unrecognised columns are kept per-row in `SampleDraft.extras` and offered for manual mapping — data is never silently dropped. Template helper text ("erforderlich/required") is filtered by `is_noise()`.
- **Controlled vocabularies are enforced server-side.** `material` / `type` / `fraction` must exist in `material_t` / `sampletype_t` / `fraction_t`; near misses are *suggestions*, never silent coercion, and `commit.py` re-validates the browser payload and falls back to `"undefined"`.
- **Lab values vs customer values.** The customer's own material text is only a *grouping key*. Step 3 groups rows by it and the operator assigns the lab's `type` / `material` / `fraction` plus prep steps 1–5 (`method_t`) per group — **one table row per group**, not a card — with a tick-rows-and-apply toolbar for arbitrary selections (Apply / Exclude / Include / Clear), and per-row overrides in the table. Whether a row is imported is a small switch (`.import-switch`, a styled checkbox with `role=switch`); unset lab values read as warning-tinted selects. The table's column pills start with **every mapped column that has an entry shown and only empty ones hidden** (`isColumnShown` in `sample-import.js`); a pill click overrides that per column. There is no fixed hidden-column list any more (weight / description 2 used to start hidden). Only an exact lookup hit is pre-applied; fuzzy suggestions wait for a click. Suggestions are offered for **material only** (spelling similarity says nothing about a sample type or fraction), need a ratio ≥ `GROUP_SUGGESTION_MIN_RATIO` (0.6), and render as a quiet unlabelled "a · b" text line under the select. Prep step 1 defaults to the `none` method and lab type to `arch` (`DEFAULT_LAB_TYPE` in `sample-import.js`).
- **Submitter / invoice.** Choices on the left as one compact radio list — scored candidates, *Pick another …* (opens a search over all submitters), *Create a new …*; on the right what the choice means. For a stored record, **the sheet and the record side by side** (`renderComparison` in `sample-import.js`): every contact value the sheet gave with its cell address, the record's value beside it, and a record value that differs from the sheet flagged (≠, warning tint) — so a returning customer's new address or e-mail is spotted. The import never updates a stored record; the note links the submitter page instead. Candidates and browse results carry the record's contact fields as `record` (`service._record_values`) for this. Create-new shows the full editable field set (incl. `salutation`, `title`, `language`, `user_comment` — `language` selects the e-mail template). The invoice recipient is a *second* `user_t` row linked via `project_t.invoice_nr`, and is matched independently.
- **Duplicate projects.** When the chosen submitter already has a same/similar-named project, the wizard offers *add to that project* or *create a separate one* with a suggested `<name>_<Month>_<Year>`. Appending skips project creation and leaves the existing project's settings untouched. When there is no clash (new submitter, or nothing similar on file) the same `<name>_<Month>_<Year>` suggestion still shows above the Project Name field as a one-click *Use the suggested name* — never applied automatically (`renderDuplicatePrompt`).
- Project fields come from lookup tables: `projecttype_t`, `research_t`, `reporttype_t`, `advisor_t` (supervisor), plus priority 0/1/2 and the `free_of_charge` / `return_to_sender` / `prep_return_to_sender` flags.
- Intake defaults (`commit.py`): `status='planned'`, `priority=1`, `price='300'`, `in_date=today`, `desired_date=+90 days`, sample `type/material/fraction='undefined'`, `editable=1`.
- **Sample column types and widths come from `models.Sample`, which mirrors the live `sample_t` exactly** (MySQL runs in strict mode: too wide a value or text in a numeric column fails the whole import). The field registry carries each column's `kind` (`text | number | integer | date`) and `max_length`; `commit._build_sample_payload` converts and clamps by them, and `_validate_payload` rejects an unreadable number before any write. `tests/test_import_column_types.py` snapshots the live schema — change the model and the snapshot together. Contact and project widths are still hand-listed (`_CONTACT_WIDTHS` / `_PROJECT_WIDTHS`), because the `Submitter`/`Project` models were not re-checked.
- **No-preparation samples skip the prep queue.** When prep step 1 is `none` and steps 2–5 name no real method (`commit.needs_no_preparation`), the import sets `prep_end` to today, so the sample lands in *Waiting for Graph* instead of *Planned*. `prep_start` stays empty. The Lab values step announces the affected row count (`labNotices()` mirrors the rule).
- **Extra analyses step.** After Lab values, a compact table (row, label, lab material) with two per-row checkboxes — `CNIsotopA` (C/N isotope analysis) and `DendroA` (dendro analysis); each column head carries its own "n of N" count and All / None. Not in the Excel sheet (maybe later), so they are operator-set, default off, kept in `sample.values.cn_isotop_a` / `dendro_a` and sent as 0/1. `commit._build_sample_payload` applies them last via `_flag()` so a sheet column cannot override them; `c_n_isotop_a` / `dendro_a` / `c_n_isotop_a_moved` are in `BLOCKED_TARGET_COLUMNS`.
- **"Import samples" asks first.** It is the wizard's last step (now the Extra analyses step) and writes at once, and operators expected another page before saving — so the button opens a `<dialog>` (`data-commit-dialog`, `confirmCommit()` in `sample-import.js`) saying so, with a summary (row count, submitter, invoice recipient, project). Only **Yes, import** commits; *No, go back* and Esc leave the operator on the Extra analyses step. *No* has the initial focus so a stray Enter cannot import.
- A commit creates, in one transaction: submitter (reused or new) → optional invoice recipient → project (new or existing) → one sample per row, each with preparation #1 carrying its prep steps, and target #1.
- **Setup → E-mail has a *Send a test e-mail* panel** (`POST /setup/email/test`). It posts the fields as currently typed — unsaved edits included — so settings can be verified before saving; a field sent empty is honoured as empty (blanking the username really does test an unauthenticated relay). The **password is the one exception**: it is never rendered back into the page, and blank means "reuse the stored one" both here and on save. Test sends never copy the configured Bcc.
- **Confirmation e-mail is never sent automatically.** After a commit the wizard renders the message (recipient, subject, body with `MAMS-<nr>` numbers paired to the customer's labels) and the operator edits, skips, or clicks Send. SMTP settings and per-language templates live in Setup → *E-mail*. `EmailSettingsStore.resolve_template_code()` decides the template: the operator's pick → the submitter's `language` → **German when no language is stored** (`NO_LANGUAGE_TEMPLATE`; true of ~99 % of `user_t` rows) → English for a language with no template of its own. The e-mail step shows a **Template** select with a one-line reason; switching re-renders subject and body via the preview endpoint (`template` in the payload), asking first if the operator has edited the text, and keeps the To field. Mail failures never roll back the import — the records are already committed.

## Sample Photos
- Each sample is photographed on receipt; the files live in one shared folder (sub-folders allowed) and are linked to a sample **only by file name: the name starts with the sample number** (`48211.jpg`, `48211b.jpg`, `48211_back.png`). There is no DB link — `sample_t.photo` is an unrelated legacy text field; don't read or write it for this.
- The lab's folder is `\\192.168.123.30\KTA\SAMS Images` (seeded in `setup_data.example.json`; on a Mac with the share mounted: `/Volumes/KTA/SAMS Images`). Photos sit in range sub-folders (`1-10000`, `10001-15000`, … `90001-95000`, plus `new` / `other`): ~44 000 JPEGs, median ~1.3 MB, a full scan takes ~1 s. **Never derive the sub-folder from the sample number** — several hundred files sit in the wrong range folder; the scan finds them because it matches on the file name alone.
- **The number must end at a non-digit.** The legacy Delphi glob `<nr>*.jpg` also returned `482110.jpg` for sample 48211; `sample_nr_from_filename` takes the whole leading digit run instead. Leading zeros are tolerated.
- **Group photos** (one picture of several samples) are listed on every sample they name, after that sample's own photos and with a "Group photo" badge. `sample_nrs_from_filename` only accepts further numbers chained directly onto the first with `-`, `_` or `+`, within `GROUP_MAX_SPAN` (100) of it: `25328-25337.jpg` is a range; `16191_16192.jpg` / `16881+16882b.jpg` / `12419-12420-12423.jpg` are lists and must be written out in full. **A short number after a dash abbreviates a range** (lab convention, confirmed 2026-10-01): it replaces the last digits, `11584-7` = 11584–11587, `14518-20` = 14518–14520 — unless the result is not above the start (`11813-2` stays on 11813). An underscore never abbreviates: `36231_2` is photo 2 of 36231. On the real folder this gives 62 group photos, all checked by hand.
- The folder is set in Setup → *Sample Photos* (`setup_data.json` section `sample_photos`, `{"folder": "<absolute path>"}`); blank switches the feature off. It is the path as seen by the **server process** — on a Windows service that means a UNC path, not a mapped drive letter.
- **No request may wait on the share.** `SamplePhotoLibrary` walks the folder in a background thread into an in-memory index (`sample_nr -> relative paths`), waits at most `wait_seconds` for it and otherwise answers `scanning`; a scan out for more than `stalled_after_seconds` is reported as `unavailable`. The index is reused for `ttl_seconds` (120 s) and a stale one keeps being served while the rescan runs. A dead mount can hang a filesystem call for minutes — never add a synchronous `os.listdir`/`glob` of the photo folder to a page route.
- **Folder errors must say why, and for whom.** `scan_photo_folder` opens the top folder with `os.scandir` so the OS's real reason surfaces — `Path.is_dir()` answers False for "access denied" too, and on the first server install that turned a permission problem into a misleading "Folder not found". `diagnose_folder_error` turns the OS error into a `FolderProblem` — **title** (what happened), **advice** (what to do), plus `folder`, `account` and the raw `os_error` — and names the two sessions that cannot see a share that works in Explorer: a **Windows service** (LocalSystem: no mapped drives, logs in as the computer account) and a program started **as administrator** (separate session without the user's drive letters or share connections). Windows error codes are checked **before** the exception class, because Python raises `FileNotFoundError` for "network path not found" (53, 67). Error **71** means the file server's client limit is reached (a desktop Windows allows 20) — met on the lab server, together with an elevated start. Unreadable sub-folders are skipped but reported by the Folder check.
- **The sample page never shows "no photos" for a share it cannot read.** Unavailable listings carry `problem` (JSON) and render as a notice with title, advice, the facts, *Try again* and a *Folder check* link. If the share drops after a good scan, the per-file `stat` fails: anything but a plain missing file (`_is_plain_missing`) turns the listing unavailable, and when every listed photo is missing the folder itself is probed once. A stalled scan is reported as "… is not answering".
- The sample page therefore renders the **Photos** group empty and `sample-photos.js` fills it from `GET /api/samples/{nr}/photos`, whose `state` is `ok | scanning | not_configured | unavailable` (always HTTP 200). The refresh icon calls it with `?refresh=true` to force a rescan right after new photos were dropped in.
- Files are served by `GET /samples/{nr}/photos/{relative_path}` (`?download=1` for an attachment). The path from the URL is **never joined to the folder blindly**: `SamplePhotos.resolve` only accepts a path the scan found *for that sample*. Keep it that way — it is what rules out `..` traversal and reading other files.
- The file response sets `Content-Encoding: identity` so `GZipMiddleware` passes images through, and the URL carries `?v=<mtime>` so a replaced photo gets a new URL.
- Browser-viewable formats (`VIEWABLE_EXTENSIONS`: jpg, jpeg, png, gif, webp, bmp) get a thumbnail and open in the viewer; `DOWNLOAD_ONLY_EXTENSIONS` (tif, tiff, heic, heif) are listed as download-only tiles. Thumbnails are the original files scaled by the browser — there is deliberately no Pillow dependency.
- The viewer is one `<dialog>` built by `sample-photos.js`: wheel / pinch / `+` `-` zoom around the cursor, drag to pan, double-click toggles fit ↔ actual size, `0` fit, `1` actual size, `←` `→` previous/next, `Esc` close. Its key handler captures on `document` and stops propagation so the record shortcuts (`[`, `]`, …) cannot fire underneath.
- `style-photos.css` and `js/sample-photos.js` load only on the sample page (`extra_styles` / `extra_scripts`), like the bench assets.

## EA Checks and QC Sign-off
- Daily check of each elemental analyzer with a check standard (acetanilide): an ISO 17025 intermediate check, **not** a calibration. Design and rationale: `docs/adr/0005-qc-signoff-and-ea-checks.md`; DDL: `docs/sql/0005_qc_ea_checks.sql`, one script for all three tables (created by hand; pages say "not set up yet" until they exist — `SamsRepository.missing_qc_tables`). **A column added later goes into that `CREATE TABLE` for new installs, an `ALTER TABLE` for databases that already have the table, and `SamsRepository.QC_LATER_COLUMNS`**, so a database without it gets the notice naming `table.column` instead of a 500 from the ORM.
- Each check may carry the **weight of the standard** (`weight_mg`, optional, (0, 100] mg — larger is treated as a unit slip). Shown in the history, the sign-off print and the API.
- **Entry strip** `_ea_check_strip.html` (+ `ea_strip_context()` in `routers/pages_ea_checks.py`) sits at the top of Lab → Graphitization and Lab → EA Checks: one card per EA, number box + draggable gauge per element (native `<input type=range>` under a drawn track; snap = the element's `step` from Setup, 0.1 by default), staff chips (last pick in `localStorage`), required comment when out of window. **An untouched gauge never submits a value** — only the number box carries `name=value_<el>`, and it stays empty until typed or the needle is moved. Several checks per day are normal; an EA's status is its latest non-voided attempt. **On the graphitization bench the strip is one line** (`ea_strip_compact`, set by `lab_queue.html` with `{% with %}`): EA name, status pill and a *Log check* / *Details* button per EA, which opens that EA's card below the line (`data-ea-open` in `ea-checks.js`; a resize event redraws the gauges, which were measured while hidden). All cards open when a check was just rejected. Lab → EA Checks keeps the full cards.
- **Records are never updated or deleted**: a mistyped check is voided (`POST /lab/ea-checks/{id}/void`, reason + who); a signed-off check cannot be voided. Each row snapshots the standard's lot, reference and window.
- **Statistics** (`ea_checks.summarize`, the only place they are computed — page, review dialog, sign-off snapshot and print view all use it): n, failed, workdays without check, and per element mean / s / bias / ±2s / ±3s / outside ±3s. Mean, s and bias use **passed** checks only.
- **QC sign-off is generic** (`qc_signoff.py`): a `SignoffSubject` per kind (`items`, `summarize`, `describe`, `body_context` + `body_template`), registered in `signoff_subjects()`. Routes `POST /qc/signoffs` and the printable `GET /qc/signoffs/{id}` know no subject. **To add OXA2 / blanks / IAEA sign-offs:** one handler + one `templates/qc/_<subject>_signoff_body.html`; no DDL. Items are linked through `qc_signoff_item_t` (unique per item), so BATS-owned rows can be signed without altering their tables.
- **The Graph Batch Builder does not look at EA checks** — no warning, no block. Batches are often built days before graphitization and are not tied to a particular EA check (removed 2026-11 at the lab's request; it used to dot system pills whose EA had no passing check today).
- Dashboard: "EA checks today" strip at the foot of the Lab queues panel (`EaCheckLog.dashboard_tile`): one dot + state per EA, overdue sign-off (Setup → EA Checks → reminder days) and a *Log check* link.
- `style-ea-checks.css` / `js/ea-checks.js` load only on the graphitization, EA Checks and sign-off print pages. The control charts are hand-drawn inline SVG (no chart library); the y-axis spans the pass window (Setup → EA Checks), widened only to keep every point on the chart.
- **`data-table-plain`** on a `<table>` opts it out of `table-tools.js` (no search/sort/export/wrap) — for small key/value tables such as the statistics block or a printed record.

	- **Lab queues**: one bar per queue in lab-path order (To prep all → In prep → Waiting for graph → Waiting for meas, then Express); each bar links to its table (`#tbl-<queue>`). **To prep all** (key `planned`, kept for the API and the `#tbl-planned` anchor; renamed from *Planned* 2026-11) has two parts drawn indented under it (`is-subset`): **To prep bone** and **To prep tooth** — the same query plus an exact `sample_t.material` filter (`TO_PREP_MATERIAL_QUEUES` in `repositories.py`, bound as `:material`; *cremated bone* is a separate material and not included). (Bars scaled to the largest queue were dropped 2026-11: they suggested a "full queue" no number backed.) The *Include held samples* toggle and the refresh icon sit in this panel's head (the toggle only affects the To prep queues) and submit on change. The EA checks strip is its footer.

Faint red / yellow zones in the track mark the thresholds, and the value reads `11 / 15` while below green. A standard without a rule falls back to the largest stock.
